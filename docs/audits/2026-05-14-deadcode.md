## Addendum: `deadcode` reachability findings (2026-05-14 main-session append)

**Tool:** `golang.org/x/tools/cmd/deadcode` (installed via `go install
golang.org/x/tools/cmd/deadcode@latest` against `golang.org/x/tools v0.45.0`, `go1.26.3`).

**Commands:**
- `deadcode ./cmd/bt/...` (main-only reachability)
- `deadcode -test ./cmd/bt/...` (include test executable entry points)

**Why this differs from `unused` / staticcheck U1000:** `unused` is a lexical check (a symbol
has no references in source). `deadcode` performs whole-program Rapid Type Analysis (RTA) from
`main` and reports functions/methods that are referenced but unreachable in the call graph.
This catches exported helpers, constructor chains, and entire subsystems that survive the
source layer but are orphaned at the binary level - a class of finding the 14 candidates above
do not cover.

- `_tmp/deadcode-cmdbt-with-tests.txt` (310 unreachable funcs, with `-test`)

- **`pkg/correlation` (32 unreachable)** concentrates in cache + correlator internals. Likely

### `-test` results (310 total)

### Tool caveats (from `deadcode -help`)

- "Just because a function is reported as dead does not mean it is unconditionally safe to
  delete it. For example, a dead function may be referenced by another dead function, and a
  dead method may be required to satisfy an interface that is never called."
- Analysis is valid only for a single GOOS/GOARCH/-tags configuration. Windows-amd64
  results may differ from Linux/macOS for any platform-gated code (none apparent in bt
  but worth noting).
- `//go:linkname` directives are not understood; not applicable to bt (no linkname usage).
