# bt-hczb Implementation Plan: UUID-keyed projects registry + UUID-anchored anchor

**Status**: draft, 2026-05-06
**Bead**: bt-hczb (P2, area:data, area:cli)
**Builds on**: bt-u8iz / bt-i1bw (registry primitive + dual-stamp), bt-mxz9 Phase 2 (anchor lifecycle)
**Unblocks improvements in**: bt-khhk (`bt robot --prefix`), bt-ni64 (`bt projects` CLI)
**Coordinates with**: sym-34ta (sym Project Identity Layer; convention-only coupling)

## Overview

bt's identity model conflates label with identity. The registry at `~/.bt/projects.json` is keyed by **prefix** (`bt`, `cass`, `sym`); `~/.bt/settings.json::anchor_project` is keyed by **path**. Both are mutable rendering attributes pretending to be primary keys. Renaming a beads project (`bd rename-prefix`) or moving it on disk fragments the registry into ghost entries and strands the anchor.

**The reframe**: bd already authors a stable identity in `.beads/metadata.json::project_id` (a UUID, created at `bd init`, never changes). bt should adopt that UUID as the canonical key, demote prefix and path to renderable attributes, and let the rename trail accumulate as `prefixes_seen` on the entry.

**The primitive change**: `Registry = map[uuid]Entry` in place of `map[prefix]Entry`. The user-facing API (`Lookup(r, prefix)`, `LookupAndValidate(prefix)`) stays prefix-driven via an internally-built reverse-index. Migration from the old shape is transparent on next `Load`.

**The settings change**: `Global.AnchorProject` (path) becomes `Global.AnchorProjectID` (UUID). `Anchor()` resolves to a path via the registry at boot. The bt-mxz9 "anchor invalid; re-anchor" UX is preserved.

**Surface area**: `pkg/projects/` schema + migration, one extension to `internal/datasource/metadata.go`, one rewrite at `cmd/bt/root.go::stampLaunchProjects` (drop the dual-stamp hack), `internal/settings/global.go` field rename + migration. Four commits.

## Architecture (L8 lens)

### Identity rule (the single architectural decision)

> **When `.beads/metadata.json` exists at a path, that file's `project_id` is bt's authoritative identity record for that project.**

Everything else is a derived view:
- **UUID** = stable identity. Machine handle. Never user-visible by default.
- **Prefix** = current human label. Mutable. Used in lookups and rendering.
- **Path** = current physical location. Mutable. Used by consumers that need filesystem access.
- **`dolt_database`** = current database name. Mutable. Free byproduct of reading metadata.json; unblocks bt-ni64's table without a follow-up schema bump.

The registry's job is to maintain (uuid -> {current prefix, current path, last_seen, prefixes_seen}) so consumers can walk in either direction. The prefix-keyed lookup remains the user-facing API; the UUID is internal-canonical.

This rule is the same convention sym-34ta needs. We document it in AGENTS.md so future agents (and sym, when its Project layer ships) converge by reading the same source, not by sharing storage.

**Boundary**: bt reads identity from `metadata.json` only. bd internally stores the same `project_id` in two places — `metadata.json::project_id` AND the Dolt `metadata` table key `_project_id` — and reconciles them via `bd doctor` (`cmd/bd/doctor/fix/metadata.go`). Bt does not reach into the Dolt table for identity, ever. The file is the boundary; the DB is bd's internal consistency model.

**Cross-machine consistency**: `bd init` adopts an existing `_project_id` from a remote Dolt database when bootstrapping (verified at `bd:cmd/bd/init.go:872-892`, gated by `--database` or auto-bootstrap from a remote whose Dolt history already carries a `_project_id`). ADR 0002 codifies this as Invariant 1 — single-source identity resolution. Practical implication: clones of the same project across machines converge on the same UUID, so bt's registry is the same identity regardless of which machine it sits on. Path is per-machine (already excluded from sync); UUID is portable.

### Why UUID primary, not prefix

Prefix is mutable. `bd rename-prefix` is a supported upstream operation. Users also rename project directories on disk. When prefix is the registry key, the registry has no representation for "same project, prefix changed." It accumulates ghost entries (live evidence: three for one project). UUID is bd-authored at `bd init` and never changes. It is the only stable referent.

The dual-stamp hack at `cmd/bt/root.go::stampLaunchProjects` (stamp both `bd` and `beads` keys against the same path, so consumers can look up via either label) is exactly the smell. Two labels, one identity. UUID indexing collapses this to one entry with `prefixes_seen: ["bd", "beads"]` and the dual-stamp code goes away.

### Why keep the user-facing API prefix-driven

Consumers (`pkg/ui/model_modes.go::resolveHistoryPath`, the future `bt robot --prefix` from bt-khhk, the future `bt projects` CLI from bt-ni64) all take their prefix input from a bead ID's hyphen-prefix or from a user flag. The user types `bt`, not `6fd231df-...`. The reverse-index `prefix -> uuid` is built in memory at `Load` time and rebuilt on every stamp. UUID-keying is an internal invariant.

`LookupAndValidate(prefix string) (path, ok)` keeps its existing signature and behavior. Existing callers do not change.

### Migration philosophy: transparent, in-place, no migration flag

bt is pre-alpha. The registry is a cache (the package doc says so explicitly: "deleting it has no consequence beyond requiring a relaunch from each project to re-stamp"). Risk is bounded: in the worst case the user deletes `~/.bt/projects.json` and relaunches bt in each project once.

`Load` detects the old shape (string keys with no `project_id` field on the entry) and re-keys in-process by walking each path's `.beads/metadata.json`. The re-keyed registry is written back on the next `Save`. Paths whose `metadata.json` is missing or unreadable get a synthesized id (`synth:<sha256(canonical-path)>` truncated to UUID-shape). Synth ids are unambiguously distinguishable from real UUIDs and stable per machine. They survive until the user launches bt in that project once with a real bd init present, at which point Stamp upgrades the entry to the real UUID.

No `bt migrate-registry` command. No `projects.v2.json` file. No dual-write transition.

### Why not move storage to `~/.config/bd-tools/registry.json`

Cross-tool identity convergence (the bead's "why this matters" framing) does not require shared storage. It requires all tools to read `metadata.json::project_id` the same way. Sym, when sym-34ta lands, can keep its own per-tool cache and converge on identity by sourcing UUIDs from the same authoritative file. Shared storage adds:

- Ownership/lifecycle ambiguity (which tool prunes? which tool migrates schema?).
- Concurrent-writer protocol (today bt is single-author per file; shared storage breaks that).
- A coupling surface across independent toolchains.

The trigger for shared storage is the second consumer actually emerging and demonstrating that the convergence-by-convention approach falls short. Until then: stay in `~/.bt/projects.json`, document the rule in AGENTS.md, ship.

### Anchor: same demotion

`anchor_project` (path) has the same problem as the registry. Live evidence: anchor points at `tools/cass` even though cass was renamed to sym and the working dir is `tools/sym`. Replace the field with `anchor_project_id` (UUID); resolve to a path via the registry at boot. The cold-boot flow established in bt-mxz9 Phase 2 still needs a path to `bd -C` against; the lookup happens once, at boot, inside `Anchor()`. If the UUID resolves to a stale or missing path, the existing "anchor invalid; re-anchor" UX (already wired) fires.

Drop the legacy field outright. No dual-write. The migration runs once: if `anchor_project_id` is empty and `anchor_project` is non-empty, resolve the path's UUID via metadata.json + registry, write `anchor_project_id`, blank `anchor_project`, save. If the legacy path no longer has metadata.json, blank both fields and surface the "no anchor" message on next cold boot.

### Future-proofing for bt-khhk and bt-ni64

- **bt-khhk** (`bt robot --prefix bd`) calls `LookupAndValidate(prefix)`. Surface unchanged.
- **bt-ni64** (`bt projects list`) renders the new fields naturally. The `prefixes_seen` slice is the rename trail column the user gets for free. The `dolt_database` field is the column bt-ni64's design already wants.

Neither follow-up is blocked or reworked by this change. They benefit at zero rework cost.

### Testability of the primitive in isolation

Same shape as bt-u8iz Phase 1. `pkg/projects/` is unit-testable without touching git, correlation, or the UI:

- Round-trip serialization of the new shape.
- Migration from the old shape (string-keyed) to the new shape (UUID-keyed) on `Load`.
- Synth-id fallback when metadata.json is absent.
- Prefix collision resolution (current-prefix wins; ties break by recency).
- Reverse-index rebuild on every Stamp.
- Backward-compat read of mixed shapes (real UUID entries + legacy string-keyed entries in the same file mid-migration).

Integration tests in `internal/settings/global_test.go` and `cmd/bt/projects_stamp_test.go` cover the anchor migration and the stamp-site rewrite respectively.

### Sequence rationale

- **Phase 0 inside Phase 1**: trivial extension to `metadata.go` (adds one struct field + helper function `ReadProjectID(beadsDir)`). No reason to ship as a separate commit.
- **Phase 1 before Phase 2**: Phase 2 needs `ReadProjectID` and the new `Stamp` signature. Phase 1's tests do not depend on the stamp site.
- **Phase 2 before Phase 3**: anchor migration depends on the registry being UUID-keyed (the migration walks the registry to resolve `anchor_project` path -> UUID).
- **Phase 4 last**: documentation reflects shipped behavior, not aspirational state.

## User experience (PdM lens)

### What the user sees

- **First launch after Phase 1 ships**: one quiet migration on the next bt invocation. No prompts. No notifications. Old entries either consolidate by UUID or get synth ids. The user can `cat ~/.bt/projects.json` and see a UUID-keyed file.
- **Live verification of bt-hczb's headline fix**: open `~/.bt/projects.json` post-migration. The three cass/sym ghost entries collapse to one entry under sym's UUID with `prefixes_seen: ["cass", "sym"]`. The anchor in `~/.bt/settings.json` is now `anchor_project_id` pointing at bt's UUID.
- **Renames going forward**: rename a beads project (`bd rename-prefix old new`). Next bt launch in that project stamps the same UUID, updates `prefix` to `new`, appends `new` to `prefixes_seen`. No fragmentation.
- **bt projects CLI (when bt-ni64 ships)**: gains a "Prev" or "History" column showing `prefixes_seen[1:]`. No follow-up registry change required.

### Edge cases worth naming

| Scenario | Behavior |
|---|---|
| Existing user, registry has prefix-keyed entries, all paths reachable + have metadata.json | Migrates cleanly; UUID-keyed; `prefixes_seen` populated from each entry's prefix-key |
| Existing user, registry has a stale prefix entry (path moved or deleted; no metadata.json reachable) | Synth id assigned to the stale entry; entry preserved (don't drop user data on migration) |
| Existing user, two entries point at the same path, both reach metadata.json with the same UUID | Entries collapse to one; both prefix-keys appended to `prefixes_seen` (dedup); most recent `last_seen` wins |
| Existing user, two entries point at the same path, only one reaches metadata.json | Reachable entry gets the UUID; unreachable entry gets a synth id (different identity from bt's perspective). Acceptable: the unreachable entry is already a ghost |
| User deletes `~/.bt/projects.json` | First-launch creates the new shape directly; no migration path runs |
| User edits `~/.bt/projects.json` by hand to a malformed shape | Existing "treat as empty registry, debug-log, next stamp rewrites" semantics preserved |
| `metadata.json` exists but has no `project_id` field (very old bd version) | `ReadProjectID` returns `("", false)`; entry gets a synth id. User upgrades bd; next stamp upgrades the entry |
| `bd rename-prefix` runs while bt is in registry but bt is not running | Next bt launch stamps the same UUID with the new prefix; old prefix lands in `prefixes_seen` |
| User runs `bd backup-restore --force` from another project's backup at the same path | bd swaps `metadata.json::project_id` to match the restored DB (`bd:cmd/bd/backup_restore.go:81-89`). Next bt launch stamps under the new UUID; the old UUID's entry persists as a ghost (path no longer points there logically). User can manually prune via the future `bt projects prune` (bt-ni64). Acceptable — force-restoring a different project's backup is an explicit identity swap, not a silent drift |
| `metadata.json::project_id` contains the all-zeros sentinel (`00000000-0000-0000-0000-000000000000`, the global-DB sentinel) | `ReadProjectID` returns the sentinel; bt treats it as no-id and falls through to synth-id. Defensive guard; not expected to fire in practice (global DB lives outside any cwd-mode project dir) |
| `anchor_project` migration: path resolves to a UUID already in the registry | Settings switches to that UUID. Done |
| `anchor_project` migration: path no longer has metadata.json | Blank both `anchor_project` and `anchor_project_id`. Next cold boot surfaces "no anchor available" message; user re-anchors by booting from inside any project |
| `anchor_project` migration: path has metadata.json but UUID is not in registry yet | Resolve path -> UUID directly; write `anchor_project_id` even though registry is silent on it. Next stamp from that project will populate the registry |

## Implementation (engineer lens)

### Phase 0 + Phase 1: Registry primitive + metadata extension

**File: `internal/datasource/metadata.go`** - add a small helper.

```go
// globalDBSentinel is bd's well-known UUID for the project-agnostic global
// database (bd:internal/doltserver/doltserver.go:101). bt should never key
// the registry on this value — global mode is consumed via DiscoverSharedServer,
// not via cwd-mode stamping, and a stamped sentinel would conflate per-project
// identity with the cross-project meta-DB.
const globalDBSentinel = "00000000-0000-0000-0000-000000000000"

// ReadProjectID returns the project_id UUID from .beads/metadata.json. Returns
// ("", false) if the file is missing, unparseable, the field is empty, or the
// value is the global-DB sentinel. Used by pkg/projects to key the registry by
// stable identity rather than by the mutable prefix label.
func ReadProjectID(beadsDir string) (string, bool) {
    metaPath := filepath.Join(beadsDir, "metadata.json")
    data, err := os.ReadFile(metaPath)
    if err != nil {
        return "", false
    }
    var meta struct {
        ProjectID string `json:"project_id"`
    }
    if err := json.Unmarshal(data, &meta); err != nil {
        return "", false
    }
    id := strings.TrimSpace(meta.ProjectID)
    if id == "" || id == globalDBSentinel {
        return "", false
    }
    return id, true
}
```

Minimal test: round-trip with a real-shape `metadata.json` fixture; missing file returns false; malformed JSON returns false; sentinel `00000000-0000-0000-0000-000000000000` returns false.

**Files: `pkg/projects/registry.go`, `pkg/projects/registry_test.go`** - schema + migration.

New `Entry` shape:

```go
type Entry struct {
    Prefix        string    `json:"prefix"`
    DoltDatabase  string    `json:"dolt_database,omitempty"`
    Path          string    `json:"path"`
    Subdir        string    `json:"subdir,omitempty"`
    LastSeen      time.Time `json:"last_seen"`
    PrefixesSeen  []string  `json:"prefixes_seen,omitempty"`
}

// Registry is keyed by project_id (a UUID from .beads/metadata.json) when
// available, or by a synthesized id ("synth:<sha256(canonical-path)>" truncated
// to 32 hex chars) when metadata.json is unreachable.
//
// Consumers do not interact with keys directly. Lookup and LookupAndValidate
// take a prefix string and resolve via an internal reverse-index.
type Registry map[string]Entry
```

New `Stamp` signature - takes the resolved id from the call site:

```go
// Stamp records or updates the entry for id, using prefix as the new current
// prefix and appending it to PrefixesSeen if it differs from the prior current.
// PrefixesSeen is ordered oldest-first, newest-last, deduped, and capped at
// the 5 most-recent entries by dropping from the front when full.
//
// The id should be a project_id UUID from .beads/metadata.json when available;
// otherwise a synth id (see SynthID). The caller resolves the id; this function
// does not read filesystem state.
func Stamp(r Registry, id, prefix, doltDB, absPath, subdir string, now time.Time) Registry
```

User-facing lookup unchanged in shape, rewritten internally:

```go
// Lookup returns the entry whose current prefix matches the argument. Falls
// back to the most-recent entry where the prefix appears in PrefixesSeen if
// no current-prefix match exists. Returns (Entry{}, false) on no match or
// when the entry's path is no longer a git repo.
func Lookup(r Registry, prefix string) (Entry, bool)

// LookupAndValidate is unchanged in signature.
func LookupAndValidate(prefix string) (string, bool)
```

Migration on Load:

```go
// Load reads the registry. If the file is in the legacy prefix-keyed shape
// (Entry has no Prefix field set), migrates in-process to the UUID-keyed
// shape by reading each path's .beads/metadata.json. Paths without
// reachable metadata.json get synth ids. The migrated registry is returned
// in memory; the next Save writes the new shape to disk.
func Load(path string) (Registry, error)
```

Migration detection: parse the file as `map[string]Entry`; an entry whose `Prefix` field is empty (or absent in JSON) is legacy and gets re-keyed; an entry whose `Prefix` field is populated is already-migrated and passes through unchanged. Field-presence detection is more robust than key-shape detection — it survives bd's `GenerateProjectID` fallback path (`%d-%d` timestamp+PID format used when `crypto/rand` fails, extremely rare), the sentinel global-DB UUID (`00000000-...`), and any future identity format bd might adopt. Phase 1's `Stamp` always writes a non-empty `Prefix`; Phase 1+ entries are unambiguously distinguishable from legacy ones. Mixed shapes (some legacy, some new) are valid mid-migration; only legacy entries get re-keyed.

Synth id helper:

```go
// SynthID returns a stable id for a path that has no reachable .beads/metadata.json.
// Format: "synth:<32-hex-chars>" where the hex is the leading 128 bits of
// sha256(canonical-path). Stable per machine.
func SynthID(absPath string) string
```

#### Phase 1 algorithms (committed)

Behavioral pseudo-Go for the four non-trivial routines. These are implementation-bound; the public API above is the contract.

**`Load(path)`** — order of operations matters:

```go
// 1. Read file; ENOENT -> empty Registry, no error. Other read err -> wrap.
// 2. Unmarshal as map[string]Entry. Corrupt JSON -> empty Registry + debug log
//    (matches bt-u8iz semantics: corrupt cache rewrites cleanly on next Save).
// 3. Walk the map. For each entry where Prefix == "":
//    a. Treat the map key as a legacy prefix label (e.g. "cass").
//    b. Resolve a real id by reading entry.Path/.beads/metadata.json via
//       datasource.ReadProjectID. Fall back to SynthID(entry.Path) on miss.
//    c. Set entry.Prefix = legacyKey (the old map key becomes the current prefix).
//    d. Set entry.PrefixesSeen = []string{legacyKey} unless an entry under the
//       resolved id already exists in the migrated map (collapse case below).
// 4. Collapse: if two legacy entries resolve to the same id, merge them:
//    a. Keep the entry with the most-recent LastSeen.
//    b. Append the loser's Prefix to the winner's PrefixesSeen (deduped, capped).
// 5. Write the migrated map to a fresh Registry; return it. Do NOT Save here -
//    migration is lazy (disk gets the new shape on next Save by a Stamp caller).
```

**`Lookup(r, prefix)`** — current-prefix-wins, then most-recent historical:

```go
// 1. Walk r once. Collect:
//    - bestCurrent: entries where entry.Prefix == prefix.
//    - bestHistorical: entries where prefix is in entry.PrefixesSeen.
// 2. If len(bestCurrent) >= 1: return the one with the most-recent LastSeen.
//    (Multiple current matches are a data inconsistency; recency is the tiebreaker
//    and the debug log fires.)
// 3. Else if len(bestHistorical) >= 1: return the one with the most-recent LastSeen.
// 4. Else: return (Entry{}, false).
// 5. After resolving, validate the entry's Path via pathLooksLikeGitRepo. If
//    invalid, return (entry, false) so the caller can render a stale-path message
//    naming the path (matches bt-u8iz semantics).
//
// Reverse-index strategy: rebuild on every Lookup call. ~17 entries today, walk
// is O(n) and microsecond-cheap. NOT cached in Registry - keeps the type a
// pure map and avoids stale-cache bugs across Stamp+Lookup interleaving.
```

**`Stamp(r, id, prefix, doltDB, absPath, subdir, now)`** — append+dedup+cap:

```go
// 1. If r == nil, allocate.
// 2. existing, ok := r[id]
// 3. If !ok (new entry): write Entry{Prefix: prefix, DoltDatabase: doltDB,
//    Path: absPath, Subdir: subdir, LastSeen: now, PrefixesSeen: []string{prefix}}
//    and return.
// 4. If existing.Prefix == prefix (no rename): just refresh Path / LastSeen /
//    DoltDatabase / Subdir; PrefixesSeen unchanged. Return.
// 5. Rename case (existing.Prefix != prefix):
//    a. Append existing.Prefix to existing.PrefixesSeen if not already present
//       (dedup keeps order: oldest-first).
//    b. Cap: if len > 5, drop from front (oldest) until len == 5.
//    c. Set existing.Prefix = prefix.
//    d. Refresh Path / LastSeen / DoltDatabase / Subdir.
// 6. Write back r[id] = existing. Return r.
```

**`SynthID(absPath)`** — straightforward:

```go
// 1. canonical := filepath.Clean(absPath); on Windows, also ToLower for
//    case-insensitivity (the registry already stores Windows paths verbatim;
//    canonicalization here means two case-variant entries collapse to one
//    synth id, which is the desired behavior).
// 2. sum := sha256.Sum256([]byte(canonical))
// 3. return "synth:" + hex.EncodeToString(sum[:16])  // 32 hex chars = 128 bits
```

Migration on Load:

```go
func LoadFrom(path string) (*Global, error) {
    // ... existing read ...
    if g.AnchorProjectID == "" && g.AnchorProject != "" {
        if id, ok := resolveAnchorID(g.AnchorProject); ok {
            g.AnchorProjectID = id
        }
        // In either case, blank the legacy field. Migration runs once.
        g.AnchorProject = ""
    }
    return &g, nil
}

// resolveAnchorID returns the project_id for absPath, resolving via the
// projects registry first (fast path, no filesystem read), falling back to
// reading .beads/metadata.json directly (slow path, used when registry is
// silent on this path).
func resolveAnchorID(absPath string) (string, bool) {
    // Try registry first.
    regPath, err := projects.ResolvedPath()
    if err == nil {
        if r, err := projects.Load(regPath); err == nil {
            for id, entry := range r {
                if entry.Path == absPath {
                    return id, true
                }
            }
        }
    }
    // Fall back to direct metadata read.
    return datasource.ReadProjectID(filepath.Join(absPath, ".beads"))
}
```

`Anchor()` rewrite:

```go
// Anchor returns the resolved anchor path with env-var precedence:
//
//   1. BT_ANCHOR_PROJECT env var (path) - explicit override.
//   2. AnchorProjectID resolved via projects registry to current path.
//   3. Empty string (no anchor available).
//
// The env var stays path-based for compatibility with existing scripts that
// `export BT_ANCHOR_PROJECT=/path/to/project`. UUIDs are an internal
// invariant.
func (g *Global) Anchor() string {
    if v := strings.TrimSpace(os.Getenv(AnchorEnvVar)); v != "" {
        return v
    }
    if g == nil || g.AnchorProjectID == "" {
        return ""
    }
    regPath, err := projects.ResolvedPath()
    if err != nil {
        return ""
    }
    r, err := projects.Load(regPath)
    if err != nil {
        return ""
    }
    if entry, ok := r[g.AnchorProjectID]; ok {
        return entry.Path
    }
    return "" // UUID is set but not in registry; surfaces as "no anchor available"
}
```

### Rollback strategy

Each commit is independently revertable:

- Revert Phase 4: just doc rollback. No behavior change.
- Revert Phase 3: anchor reverts to path-based. `anchor_project` field is re-introduced in the struct; users with `anchor_project_id` already written see it ignored on next Load (the missing field decodes to empty string). They lose their anchor and must re-anchor by booting from inside a project. Acceptable rollback risk.
- Revert Phase 2: stamping reverts to dual-stamp. Existing UUID-keyed entries in the registry stay; new stamps add prefix-keyed entries alongside, so the registry holds both shapes simultaneously. Phase 1's `Load` migration is idempotent on UUID entries (already-migrated keys pass through unchanged) and continues to re-key any new prefix-keyed entries on next launch. Consumers using the prefix lookup keep working throughout. No data loss.
- Revert Phase 1: full rollback to bt-u8iz baseline. UUID-keyed entries written by Phase 2 in the field briefly become unreadable; the existing "treat as empty registry, debug-log, next stamp rewrites" path covers this.

No data migration required to rollback. The registry is a cache; the settings file is single-author.

## Coordination notes

### vs sym-34ta

Sym is designing a Project Identity Layer (`sym-34ta`, open) that wants to read bd's `project_id` first, bt's registry second. After bt-hczb, both come from the same authoritative source - sym can read `.beads/metadata.json::project_id` directly when available, and consult bt's UUID-keyed registry as a richer cache (bt's registry knows the rename trail; bd's metadata.json knows only the current state).

If sym ships first, it can use bd's project_id directly with no bt dependency. If bt ships first (this bead), sym benefits from bt's enriched cache when present.

## Open questions to resolve during implementation

None remaining. All prior open questions resolved during plan refinement:

- **`prefixes_seen` cap = 5**. Keeps the registry file human-readable; audit history beyond 5 renames is not load-bearing for any planned consumer. Trigger to revisit: real dogfood pain showing the rename trail wanted past that depth.
- **Synth-id format = `synth:<32 hex>`** (leading 128 bits of sha256). Collision-resistance margin is cryptographically negligible; the shorter form keeps registry-file scans manageable.
- **Migration write-back = lazy** (in-memory on Load; disk on next Save). A read-triggered write is a worse UX surprise than a slightly longer migration window, and the registry is a cache - mid-transition reads are safe.
- **`detectProjectDBAt` retains current semantics** (returns the dolt_database label). The new `currentPrefix` decision branches on `inferBeadPrefix` at the stamp site only. Pre-impl grep already confirmed no other caller depends on `detectProjectDBAt` returning a bead-ID prefix.
