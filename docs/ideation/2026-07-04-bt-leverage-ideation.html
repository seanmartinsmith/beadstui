Grounding Context

Codebase Context. bt is a Go 1.25 / Bubble Tea v2 single binary with three API layers (interactive TUI, robot JSON CLI with 46 subcommands, export), 92k LOC production + 102k LOC tests, currently v0.1.2 pre-release and 100% read-only. Data layer: Dolt-only upstream (embedded default read via bd export shell-out, never-persist per bt-qrt2u; server + shared-server modes; schema v50 absorbed via COALESCE + column probing). ADR-002 (stabilize-and-ship) is largely complete; ADR-004 (unified keybinding/help) is proposed with a spike and 13 child beads. The write path is designed but unbuilt: all writes shell out to bd (no direct SQL), Pattern-C modal pickers chosen, mutation-feedback / action-context / detail-pane foundation beads open (bt-msxk, bt-3epf, bt-krx1). Backlog: 377 open beads, 0 P0, with a P1 layer containing a product-vision epic (bt-53du), a cross-project OS epic (bt-ushd), and a production-ready epic (bt-aj3l).

Load-bearing tension
The footer got a full three-zone smart redesign that shipped 2026-06-21 (bt-a3zi3) — yet the owner still finds it uninformative. Diagnosis (verified in code): the degradation engine is good; the content tiering protects bt’s own daemon chrome and drops bead substance first.
Verified external facts
Upstream docs/COMMUNITY_TOOLS.md lists ~11 TUIs, only 2 active; bt’s ancestor beads_viewer is marked “Historical/Stale, incompatible with Dolt-based beads (v0.50+)”; bt itself is not listed. Gas Town ships a first-party monitoring TUI (gt feed: agent tree / convoy / event stream). Perles (the other live community TUI) could not be confirmed as doing writes or orchestration — its README reads as a read-only BQL/kanban tool.
Owner context
Works in scrunched terminals (14–30 rows) — small-terminal is the primary case. Active beads contributor (upstream asks are a real lever). Quiet-ship posture: product quality drives adoption, targeted maintainer collaboration only.
Evidence layer
Six dossiers (TUI information surface, write path, robot CLI, data layer, upstream adoption, web research) + fresh-context adversarial verification with live fetches; checkpoints alongside this file.

1Ship the claim-first write slice as the trust release

write-path Confidence 85% Complexity Medium
Description

Invert the planned sequencing (“foundations first, writes later”): ship one real write end-to-end now — bd update <id> --claim on a single keystroke. Claim is the perfect first write: no modal, no text input (so no Windows cp1252 corruption risk), and the refresh loop already exists — a bt-initiated claim commits to Dolt, rewrites the manifest, and the content-comparing watcher reloads exactly as it does for external bd writes today. Then extract the foundations (bt-msxk feedback patterns, bt-3epf action contexts) from a live write instead of designing them speculatively. Shape the v1 write release as a governance artifact: an always-visible command-log pane showing every bd invocation verbatim with exit status (lazygit’s @ panel), a formal --readonly flag / BT_READONLY that hard-disables the mutation layer (k9s’s safe-mode), pending→settled write semantics (below), and an actor-identity decision made now — while upstream’s attribution redesign (bd-edi, P0 in-progress) is still wet cement.

Basis

direct: evidence-write-path dossier — “Claim (bd update <id> --claim): Single keystroke, no modal”; internal/datasource/metadata.go:89-99 — Dolt rewrites the manifest on every commit, “bt’s event-driven change-detection signal for live refresh”; docs/design/writable-tui-design-surface.md §3 — session attribution explicitly unresolved. external: lazygit command-log (transparency as the trust mechanism); k9s formal --readonly safe-mode. Verifier: sound; and Perles’ supposed write support could not be confirmed — if the surviving community TUIs are all read-only, the trust/governance shaping is the differentiator, not optional polish.

Rationale

This is the highest-leverage sequencing decision on the table. It collapses “bt eventually supports writes” from a horizon into a shippable slice; it validates three open foundation epics against reality before they harden; and it converts the write push’s biggest non-technical risk — a possible “bd is the canonical writer” ecosystem norm — into bt’s adoption argument, because every mutation is demonstrably a bd invocation with a visible receipt. The actor-identity leg is time-sensitive: whoever writes first sets the attribution convention, and upstream’s events redesign is in flight right now.

Downsides

Claim-first means shipping UX before the full action-context model exists — some rework risk in bt-3epf/bt-msxk. The pending/settled semantics re-litigate the pessimistic-spinner v1 default (bt-oiaj) — a deliberate re-vote, but it reopens a closed decision. --readonly and the receipts pane are extra scope for a v1 that could technically ship without them (not recommended).

2Footer shows the work, not the app

tui-information-surface Confidence 90% Complexity Low
Description

The June footer redesign (bt-a3zi3) fixed compression mechanics, not content philosophy — which is why it still reads as uninformative. Verified in code: the never-drop tier 0 is alerts / instance / worker (bt’s own daemon chrome), while bead substance (statsSection, counts, anything about the selection) is zeroed early in the reduction cascade. Invert the tier map: the protected core becomes the selected bead’s actionable state (blocked/ready, blocker count, next legal action — wired from the bt-3epf action-context model so it becomes the write-affordance surface for free), and daemon chrome degrades first. Two compatible content upgrades: a dark-cockpit discipline (quiet strip when healthy; anomalies and deltas light up — stale data, dead watcher, failed shell-out), and later an event ticker with graph-ripple facts (“bt-krx1 closed 2m ago → 3 unblocked”) once the events spine (idea 7) exists.

Basis

direct: pkg/ui/model_footer.go:1130-1133 — “Tier 0 (always keep): alerts, instance, worker status”; :1187-1188 — statsSection = "" zeroed at reduction step 5 (verified by the fresh-context checker). external: Airbus dark-cockpit / annunciator doctrine — a quiet panel means healthy; anything lit demands attention. Five of five ideation frames independently converged on this diagnosis.

Rationale

It resolves the named daily pain at its actual root with the smallest diff on this list — the Render() engine is pure and isolated; the change is reordering the tier map and redefining the core sections. Anchoring the core to the action-context model means the footer becomes the affordance surface the write era needs anyway: fix the footer once, and it is already the “what can I do next” surface when writes land.

Downsides

Content selection is opinionated — needs a real decision about what earns tier 0 (selection state vs. scope counts vs. anomalies). The event-ticker variant depends on idea 7 and should not gate the re-tiering. Small risk of churn if bt-krx1’s detail-pane redesign wants to own some of the same information.

3The 14×80 layout contract: one W×H budget, sweep-gated, agent-queryable

tui-information-surface Confidence 80% Complexity Medium
Description

bt has two responsive systems that never talk: the issues list gates columns on five inline magic widths (>60/80/100/120/140) and reserves full column width even when every value is empty (the bt-foit padding), while the footer runs its own tier cascade — and there are zero height rules anywhere. Replace both with one declarative layout-budget module: elements (columns, badges, hints, panes) declare priority and minimum size; a single allocator fits them per width and height class; columns earn cells only when their data exists under the current filter; below ~20 rows the TUI swaps to a purpose-built compact layout rather than a degraded desktop one (the watch-complication rule). Enforce it: productize the existing render harness into bt robot render --view list --width 80 --height 14 (deterministic frame + JSON layout report) and add a CI sweep across width 14–200 × height 3–30 with invariants (no wraps, footer always 1 line, ≥5 visible rows). Fold help into the command palette — a scrolling filtered list degrades at any height, which collapses bt-0h7p + bt-xavk and structurally dissolves bt-dx7k (help broken at small sizes).

Basis

direct: pkg/ui/delegate.go:73/100/111/125/138 — uncoordinated width literals (verified); delegate.go:111-118 — empty assignee still reserves 14 cells; TUI dossier — “No explicit row-height handling found” and no W×H sweep in render_harness_test.go; bt-dx7k blocked. external: cartographic generalization (different map per scale, not a shrunken one); Apple Watch “not a shrunken phone app” doctrine.

Rationale

The owner’s 14–30-row terminals make the “degraded” case the primary case, and today that case is governed by magic numbers nobody owns. One budget module turns the user’s second named complaint (columns) plus the blocked help bead plus every future TUI surface into declarations against a tested contract — and bt robot render simultaneously kills the biggest friction in bt’s own agent-driven development loop (agents being blind to the TUI) and becomes the bug-report artifact for third parties.

Downsides

The largest TUI refactor on the list; touches delegate, footer, and help simultaneously (though it can land budget-first, consumers one at a time). Per-row content-driven columns can cause visual jitter across rows if done naively (needs a column-stability rule within a viewport). Palette-as-help overturns the 16-context modal matrix — some context-specific help content needs a new home.

4The adoption ladder: certify → list → protocol

upstream-adoption Confidence 75% Complexity Medium
Description

Three rungs, each producing the evidence the next one cites. Rung 1 — certify: a CI matrix that runs bt’s e2e suite against each new bd release (plus a nightly bd-HEAD canary) across embedded / server / shared-server fixtures, publishing a passing compatibility matrix and badge; fold in the golden-file wire-stability gate (snapshot all 46 robot envelope schemas; CI fails on rename/removal, passes add-only) and the still-unbuilt fallback==tag release guard; complete first-run resilience with a bt doctor source-discovery trace (which detection branch fired, bd + schema version, manifest age, watcher liveness). Rung 2 — list: the COMMUNITY_TOOLS.md PR — verified: the doc marks bt’s ancestor beads_viewer “Historical/Stale, incompatible with Dolt-based beads (v0.50+)” and bt is absent; the successor narrative writes itself, led by the living compat matrix rather than a claim. Rung 3 — protocol: propose upstream that bd ui exec a UI binary discovered on PATH under a documented convention (the git-subcommand / gh-extension model). beads stays CLI-only by philosophy; official status becomes a protocol bt authored rather than a favor bt requests.

Basis

external: COMMUNITY_TOOLS.md fetched and verified — ~11 TUIs listed, only 2 active, ancestor flagged stale-incompatible, bt absent; gh-extension / git-subcommand / kubectl-plugin delegation precedent; gh itself adopting Charm’s huh (the CLI owner treating TUI-via-Charm as natural evolution). direct: upstream dossier — “a release-time CI guard (fallback==tag) is still unbuilt”; internal/diagnostics/diagnostics.go:1-9 covers caches, not source-mode detection (verified).

Rationale

Version drift is the documented graveyard of every prior beads TUI — and bt already carries the drift armor (column probing, v50 COALESCE) without publishing any proof of it. Certification converts existing engineering into visible trust; the listing converts an ephemeral Discord drop into a permanent front-door entry; the protocol converts “official” from someone’s goodwill into a convention bt defined. This ladder is intent (2) made concrete, and none of it depends on unbuilt product features.

Downsides

Standing CI infrastructure to maintain (bd fixture projects per version × mode). The rung-3 proposal spends contributor capital and could be declined — though rungs 1–2 retain full value on their own. Listing bt raises its visibility before the write story ships (arguably a feature: the read surface is the mature one).

6Agent-native surface: self-describing envelope + executable actions

robot-cli Confidence 80% Complexity Medium
Description

Four add-only wire upgrades that turn bt’s robot surface from “structured on success, opaque otherwise” into a self-describing agent API. (1) A per-mode capabilities block in the envelope (or bt robot capabilities): as-of, history, correlation, writes, schema versions — declared as data, so agents branch instead of pattern-matching refusal prose; when embedded gains history or writes ship, the block flips and every agent adapts with zero coordination. (2) Structured errors: code, message, supported_alternative — starting with the --as-of refusal, whose fix-suggestion currently exists only as English inside an error string. (3) actions[] order-set envelopes: triage/recommendation payloads ship the exact ready-to-exec bd argv with preconditions (the CPOE / hypermedia pattern) — bt makes bd writes correct for agents without writing anything itself. (4) TUI yank upgraded from bare bead ID to the full bt robot ... invocation reproducing the current view — which forces TUI filter state and robot flags onto one canonical model. All four sit on a single bdcmd command-builder package with three consumers: robot emit, the TUI write executor (idea 1), and the receipts pane — command construction tested once under the robot contract suite.

Basis

direct: internal/datasource/source.go:63 — ErrAsOfNotSupportedForRobot with the alternative embedded in prose (verified); pkg/ui/list_keys.go:147 — yank copies only Issue.ID (verified); robot_output.go:45-61 — RobotScope precedent for envelope self-description; docs/robot README add-only rule makes all four wire-compatible. external: HATEOAS hypermedia controls; CPOE order sets; 2025–26 agent-CLI consensus (structured errors carrying fix suggestions).

Rationale

bt’s stated identity is “the agent-consumption layer,” and its differentiation against every other beads TUI is exactly this surface — deepening it is moat-building where bt is already ahead. The actions[] + capabilities pair is also the strongest possible expression of the ecosystem’s canonical-writer norm: bt tells agents precisely what to run; bd stays the only writer. And the bdcmd package quietly builds half of idea 1’s executor.

Downsides

Wire-surface additions are forever (add-only discipline means these fields must be right the first time). actions[] preconditions can go stale between emit and exec — needs an honest “advisory, re-validate on exec” contract. Yank-as-command requires the TUI filter model cleanup first (that is the point, but it is real work).

7Events-first data spine + upstream read-API campaign

data-layer Confidence 60% Complexity High
Description

Embedded mode — the upstream default, so bt’s common case — refreshes by shelling a full bd export and re-parsing the entire project’s JSONL on every manifest change (30s timeout, 3 retries; ~0.4s per 1300 issues; the 4921-issue cross-project workspace already hurts). bt has a precise when-signal (the Dolt manifest root hash) and no what-signal. Move to the market-data architecture: an events feed as the primary change channel, full export demoted to gap/hash-mismatch recovery. Three steps: (1) manifest-hash snapshot cache under .bt/ so unchanged data is never re-exported (needs an explicit ruling that a read-side cache doesn’t violate bt-qrt2u’s never-persist boundary — precedent exists: .bt/ already holds the semantic index); (2) a single monotonic data-version signal consumed by the watcher, server-mode polling, post-write settlement (idea 1), and the footer ticker (idea 2); (3) the upstream campaign: spec and file bd export --since <hash>, bd history <id> --json, and bd events --follow as bt/bd-paired beads — bt as the reference consumer shaping bd’s read API, which also kills the --as-of robot refusal and the embedded correlation/history gap at their root.

Basis

direct: internal/datasource/embedded.go:45-52 — full export re-parse, nothing cached (verified); embedded.go:16-19 — ~0.4s / 1300 issues; metadata.go:89-99 — manifest as the change signal; bt-5uaxh — embedded correlation/history deliberately empty awaiting bd support. external: NASDAQ ITCH / OPRA snapshot-plus-incremental feed architecture; upstream’s native events table (Storage.GetEvents) exists — only the CLI access is missing.

Rationale

This is the long pole under everything else: refresh latency is the floor under write feedback (idea 1), the fuel for the footer ticker (idea 2), and the scaling wall for both fleet-sized workspaces (idea 5) and N agents hammering robot mode. The upstream campaign converts three bt workarounds into sanctioned primitives while making bt the tool whose needs are encoded in bd’s own API — the most durable form of “official” there is.

Downsides

The full payoff depends on upstream landing primitives bt doesn’t control (hence 60%); the snapshot cache and data-version unification are unilateral, but the events channel is not. Cache invalidation correctness is real work (hash-keyed helps). Needs the bt-qrt2u boundary ruling before any disk cache ships.
